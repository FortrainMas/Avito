# Поиск услуг на Авито: 50 объявлений под запрос

**Как запустить** — сразу в раздел [«Как воспроизвести»](#как-воспроизвести).

Для каждого из 2 452 тестовых запросов (файл `benchmark_queries.parquet`) нужно выбрать 50 объявлений из 189 212 объявлений услуг (файл `benchmark_items.parquet`). Этот набор объявлений дальше называем корпусом: ответы можно брать только из него. Ответов к тестовым запросам нет. Для обучения дан `train.parquet`: 497 673 строки, в каждой — поля поиска (текст, локация, фильтры, категория, флаг доставки) и объявление, которое пользователь в итоге выбрал.

Метрика — Recall@50. Для каждого запроса считается доля его правильных объявлений (тех, что выбрал пользователь), попавших в 50 ответов, и эти доли усредняются по всем запросам. Recall@N — то же для первых N ответов.

**Решение** работает в два шага. Сначала ретривер отбирает для запроса около 600 кандидатов, то есть объявлений, среди которых, скорее всего, есть правильное. В ретривере два поиска: по совпадению слов (алгоритм BM25, раздел «Бейзлайн») и по смыслу (дообученная нейросеть-эмбеддер, раздел «Эмбеддинги»). Оба учитывают, в какой локации искал пользователь. Затем реранкер, модель LightGBM, заново упорядочивает кандидатов и оставляет первые 50 (раздел «Реранкинг»).

| | Валидация, Recall@50 | Лидерборд, Recall@50 |
|---|---|---|
| Итоговое решение: поиск по словам и по смыслу + LightGBM | 0.950 | 0.922 |

Валидация — наша проверка на запросах из train, ответы к которым известны (раздел «Валидация»). Лидерборд — оценка организаторов на тестовых запросах. Бейзлайн — первое простое решение без обучаемых моделей, с которым сравниваем всё остальное. Фильтры — параметры, которые пользователь выбрал в интерфейсе поиска, например «Вид услуги Красота, здоровье». Итоговый реранкер учится в том числе на валидации, поэтому 0.950 — оценка: столько даёт та же модель, если учить её на одной половине валидации, а проверять на другой (раздел «Всё вместе»). Чем валидация отличается от теста — в конце раздела «Валидация».

Код разложен по этапам: `src/avito/<этап>` — функции, `scripts/<этап>` — запуск, `notebooks/<этап>` — исследование и замеры. Каждый раздел ниже ссылается на свой ноутбук.

## Данные

[`ingestion/raw.ipynb`](notebooks/ingestion/raw.ipynb) — колонки, пропуски и странные значения, [`ingestion/insights.ipynb`](notebooks/ingestion/insights.ipynb) — графики и выводы, [`processing/text.ipynb`](notebooks/processing/text.ipynb) — обработка текстов. Главное:

- **Тексты запросов.** В train 74 529 разных текстов запроса. Частые тексты вроде «маникюр» повторяются очень много раз: 1% самых частых текстов даёт почти половину строк train, а 60% текстов встречаются один раз. Среди тестовых запросов все 2 452 текста разные, поэтому и в валидации каждый текст встречается один раз (раздел «Валидация»).
- **Большинство выбранных объявлений не входит в корпус.** Объявление из корпуса выбрано только в 6.6% строк train (`validation/split.ipynb`). Остальные объявления поиск по корпусу найти не может, и это важно при сборке валидации.
- **Локация.** 83% выбранных объявлений лежат в той же локации, где искали. Объявление всегда привязано к конкретному городу или посёлку, а искать можно и шире: по региону («Москва и область») или по всей стране. У таких широких локаций своих объявлений нет, поэтому у 17% тестовых запросов в локации поиска нет ни одного объявления, и правило «сначала объявления из локации поиска» им ничего не даёт. При поиске по городу выбирают почти всегда в самом городе или в пригороде, при поиске по региону — в городах этого региона. Поэтому вместо такого правила используем доли выборов по локациям (раздел «Бейзлайн»).
- **Одного заголовка мало.** Все слова запроса есть в заголовке выбранного объявления только у 16% пар «запрос — выбранное объявление», вместе с параметрами — у 27%, а вместе с описанием — у 61%. Параметры — поля объявления вроде «Вид услуги» или «Куда выезжаете». Поэтому ищем по заголовку, параметрам и полному описанию. Тексты приводим к нижнему регистру и отрезаем окончания стеммером Snowball (PyStemmer).

## Валидация

[`validation/split.ipynb`](notebooks/validation/split.ipynb)

Ответов для тестовых запросов нет, поэтому качество проверяем на запросах из train, для которых ответ известен. Train делится на три непересекающиеся части:

| Часть train | Размер | Для чего |
|---|---|---|
| валидация (проверочные запросы) | 5 032 запроса | замер качества; в самом конце на ней же дообучается итоговый реранкер (раздел «Всё вместе») |
| обучение реранкера | 6 487 запросов | обучение LightGBM |
| обучение ретривера | всё остальное, 482 161 строка | доли выборов по локациям, дообучение эмбеддера |

Первым двум частям нужны запросы с правильными ответами, а третья используется как набор строк, поэтому её размер дан в строках. Доли выборов по локациям — для каждой локации поиска, в каких локациях и как часто выбирали объявления (подробнее в разделе «Бейзлайн»).

**Как из строк train получаются запросы.** В train нет номера запроса, есть только строки «поля поиска → выбранное объявление». Поэтому запросом считаем весь набор полей поиска: текст, локацию, фильтры, категорию и флаг доставки. Все строки train с одинаковыми полями склеиваем в один запрос, и его правильные ответы — все объявления, выбранные в этих строках. Один и тот же текст в разных городах или с разными фильтрами — это разные запросы. По условию задачи у тестового запроса подходящих объявлений тоже бывает несколько: «обычно одно-два, иногда больше». Но в валидации таких запросов мало: у 4 977 из 5 032 запросов правильное объявление одно (почему — ниже, в «Чего валидация не повторяет»).

**Валидация похожа на тест.**

- Поиск идёт среди тех же 189 212 объявлений корпуса, что и в тесте. Поэтому берём только запросы, у которых все выбранные объявления лежат в корпусе: иначе правильный ответ невозможно найти. Таких всего 18 436 из 354 463 запросов train, около 5%.
- В тесте все тексты разные. Если один текст встречается в нескольких подходящих запросах (например, в разных городах), в валидацию берём только один из них. Иначе в ней было бы много частых коротких запросов вроде «маникюр», которых в тесте мало.
- 37% тестовых текстов уже встречались в train. По таким знакомым текстам решение может опереться на прошлые выборы, по новым — нет. В валидации доля знакомых текстов тоже 37%; для неё она считается по train без самих проверочных запросов. Кроме того, знакомые тексты делим на группы по популярности — в скольких разных запросах train встречается текст (1, 2–3, 4–10, 11–50, больше 50) — и набираем в валидацию в тех же долях, что в тесте. Иначе в валидацию попали бы в основном частые тексты, и подсказки о прошлых выборах выглядели бы полезнее, чем на тесте. Тест здесь служит только образцом: мы смотрим на тексты тестовых запросов, а их ответов у нас нет.
- Все строки train, из которых собраны проверочные запросы, удаляются из train. Строки с тем же текстом, но с другой локацией или другими фильтрами остаются, поэтому текст проверочного запроса может быть знакомым.

**Реранкер учится на отдельных запросах.** Реранкер получает подсказки, посчитанные по train: доли выборов по локациям и похожесть текстов от эмбеддера (раздел «Эмбеддинги»). Если бы эти подсказки считались по тем же строкам, на которых учится реранкер, они «знали» бы ответ, и реранкер научился бы им слишком доверять. Поэтому реранкер учится на отдельных 6 487 запросах. Их тексты не встречаются в валидации, и хотя бы одно выбранное по ним объявление лежит в корпусе; правильными считаются только объявления из корпуса. Условие мягче, чем у валидации: для обучения достаточно, чтобы правильное объявление можно было найти, а валидация должна быть устроена как тест. Строки этих запросов тоже удаляются из train. Всё оставшееся — обучение ретривера, и доли выборов по локациям посчитаны без строк запросов реранкера. Эмбеддер учится на парах «текст запроса → выбранное объявление», и правильные ответы запросов реранкера почти не попали в его обучение: он видел только 1.2% таких пар. Это случаи, когда тот же текст запроса, набранный в другой локации, вёл к тому же объявлению (`embeddings/models.ipynb`).

**Чего валидация не повторяет.** 9% тестовых запросов ищут по всему Авито, а не только в «Услугах» (`search_category = 0`). В train таких всего 34 строки, и в валидацию попал один такой запрос из 5 032, так что проверить качество на них нельзя. Запросов без фильтров в тесте 63%, а в валидации 52%. Запросов с несколькими правильными объявлениями в валидации всего 1.1%, а во всём train — 15%: условие «все выбранные объявления лежат в корпусе» реже выполняется, когда выбранных объявлений несколько. В тесте, судя по условию задачи, таких запросов больше, а они сложнее: за запрос с двумя правильными объявлениями 1 получаешь, только если оба попали в 50 ответов. И 4.4% тестовых запросов целиком повторяют запрос из train, а в валидации таких нет, потому что строки проверочных запросов удалены из train.

Какие из этих отличий снижают результат на лидерборде, мы не проверяли. Вероятно, отчасти дело в запросах по всему Авито (как решение работает на них, мы не знаем) и в запросах с несколькими правильными объявлениями. Разница в доле запросов без фильтров, вероятно, мало что меняет: на валидации итоговое решение даёт на запросах без фильтров и с фильтрами одинаковый Recall@50 (0.950 в обоих случаях, `ranking/dense.ipynb`). По точным повторам в train выбирали объявления из корпуса в 58% строк, а в среднем по train — в 6.6%, так что ответ на них, похоже, часто совпадает с прошлым выбором. Но правило «вернуть то, что выбирали по этому же запросу» на валидации не проверить, поэтому в решение оно не входит.

## Бейзлайн: поиск по словам и локации

[`retrieval/baseline.ipynb`](notebooks/retrieval/baseline.ipynb)

BM25 оценивает, насколько объявление подходит к запросу по словам: оценка тем выше, чем больше слов запроса нашлось в объявлении, чем реже эти слова встречаются в корпусе и чем чаще они повторяются в самом объявлении. Поиск по одному заголовку даёт Recall@50 = 0.293. Поиск по заголовку, параметрам и полному описанию, склеенным в один текст, даёт 0.470; заголовок при этом повторяем трижды, чтобы его слова весили больше, чем слова длинного описания. Этого мало, потому что BM25 не знает, где искал пользователь: «сантехник» в Москве находит сантехников по всей стране.

Самый простой способ учесть локацию — поставить объявления из локации поиска выше всех остальных: 0.817. Но так не учесть поиски по региону и выборы в пригородах. Лучше работают доли выборов по локациям: для каждой локации поиска по обучению ретривера считаем, в каких локациях и как часто выбирали объявления. Например, при поиске по «Москве и области» 60% выборов приходится на саму Москву, остальное — на города области. Оценка объявления:

`BM25 / максимальный BM25 по запросу + alpha · log(p + 0.0003)`

Деление на максимум нужно, чтобы лучшее по словам объявление запроса получало 1. p — какая доля выборов при такой локации поиска приходится на локацию этого объявления. Логарифм нужен, чтобы разница между 50% и 5% значила столько же, сколько между 5% и 0.5%. Добавка 0.0003 нужна, чтобы объявления из локаций, где ни разу не выбирали, опускались, но не исчезали совсем. `alpha` — насколько локация важнее текста; его перебрали:

| `alpha` | 0.05 | 0.1 | 0.2 |
|---|---|---|---|
| Recall@50 | 0.845 | **0.873** | 0.850 |

Потом добавили фильтры: к оценке BM25 по тексту запроса прибавляем 0.3 × оценку BM25 по тексту фильтров. Фильтр описывает услугу шире, чем сам запрос, поэтому весит меньше. Итог бейзлайна — **Recall@50 = 0.885**.

Хуже всего бейзлайн работает в двух группах запросов. Если правильное объявление лежит не в локации поиска, Recall@50 = 0.74, а на остальных запросах — 0.93. На запросах из одного слова Recall@50 = 0.78. Что с этими группами стало в итоговом решении — в разделе «Всё вместе».

## Реранкинг

[`ranking/ranker.ipynb`](notebooks/ranking/ranker.ipynb)

В первые 50 объявлений бейзлайна попадает 88.5% правильных объявлений (это и есть Recall@50 = 0.885), а в первые 500 — 96.9%. Значит, многие правильные объявления бейзлайн находит, но ставит слишком низко. Поэтому берём первые 500 кандидатов бейзлайна и заново упорядочиваем их моделью, которую называем реранкером; первые 50 идут в ответ.

Для каждой пары «запрос — кандидат» считаем признаки, то есть числа, которые описывают пару: например, оценку BM25 или долю выборов локации кандидата. Реранкер — модель LightGBM: она строит одно за другим много небольших деревьев решений, и каждое следующее исправляет ошибки предыдущих. В режиме LambdaRank модель учится не угадывать отдельные числа, а правильно сортировать кандидатов внутри одного запроса. Параметры LightGBM — обычные стартовые значения, мы их не подбирали.

Признаки добавляли группами:

| Признаки | Recall@50 |
|---|---|
| бейзлайн | 0.885 |
| место и оценка кандидата в бейзлайне | 0.881 |
| + текст: BM25 и доля слов запроса отдельно по заголовку, параметрам и описанию, BM25 фильтров | 0.892 |
| + локация: доля выборов, та же ли локация, расстояние до центра локации поиска, доля кандидатов в локации поиска | 0.900 |
| + подкатегория и запрос: доля кандидатов той же подкатегории среди первых 30, длина запроса, есть ли фильтры, категория поиска | **0.907** |

«+» значит, что группа добавлена ко всем признакам строк выше. «BM25 фильтров» — оценка BM25 текста фильтров по всему объявлению. «Доля кандидатов в локации поиска» — какая доля из 500 кандидатов запроса лежит в локации поиска. Подкатегория — рубрика объявления внутри «Услуг», например «Маникюр». «Доля кандидатов той же подкатегории среди первых 30» — какая доля из первых 30 кандидатов бейзлайна относится к той же подкатегории, что и данный кандидат: если 20 из 30 — «Маникюр», кандидат из «Маникюра» получает 0.67.

Если дать модели только место и оценку кандидата в бейзлайне, она работает на 0.4 п.п. хуже самого бейзлайна (п.п. — процентные пункты, разница двух Recall@50: 0.881 вместо 0.885). Ей нужна новая информация. Дальше каждая группа признаков добавляет своё: текст — 1.2 п.п., локация — 0.8, подкатегория и запрос — 0.7. Разницы здесь и дальше посчитаны по неокруглённым значениям, поэтому могут на 0.1 п.п. отличаться от разницы чисел в таблицах. Эти приросты не случайны: 95% доверительный интервал каждого прироста не задевает ноль. Интервал считаем бутстрепом: 1000 раз случайно перевыбираем проверочные запросы с повторениями и пересчитываем разницу.

Свойства объявления (цена, рейтинг, число отзывов, длина текстов) добавляют на валидации ещё 0.6 п.п., но в итог не входят. Все правильные ответы валидации — объявления, которые встречаются в train, а такие объявления популярнее остальных: медиана числа отзывов у правильных ответов валидации — 42, у объявлений корпуса, которые встречаются в train, — 33, у остальных — 16. Ответы теста — это другие выборы, и среди них могут быть объявления, которых в train нет вовсе; в корпусе таких 171 070 из 189 212. Поэтому правило «больше отзывов — правильнее» на валидации может работать лучше, чем на тесте. Проверить это можно только на лидерборде, поэтому от этих 0.6 п.п. мы отказались.

## Эмбеддинги

[`embeddings/models.ipynb`](notebooks/embeddings/models.ipynb)

BM25 не находит объявления, у которых нет общих слов с запросом. А у 4.9% пар «запрос — выбранное объявление» нет ни одного общего слова (`processing/text.ipynb`): например, человек ищет «кафельщик», а выбирает «Плиточник сантехник». Для таких пар нужен поиск по смыслу: нейросеть-эмбеддер превращает текст в вектор так, что у текстов с похожим смыслом векторы близки. Близость измеряем косинусом угла между векторами: чем ближе он к 1, тем ближе тексты по смыслу.

Текст объявления для модели — заголовок, параметры и первые 700 символов описания. Из параметров оставляем только названия услуг, а адреса, цены, графики работы и прочее выбрасываем: это 83% символов параметров. Текст запроса — сам запрос и его фильтры. Оценку считаем как в бейзлайне, только вместо BM25 — косинус: `косинус / максимальный косинус по запросу + alpha · log(p + 0.0003)`.

Сначала сравниваем готовые открытые модели. Для каждой вес локации `alpha` подобран отдельно, в таблице — Recall@50 при лучшем `alpha`:

| Модель | Recall@50 |
|---|---|
| `intfloat/multilingual-e5-base` | 0.805 |
| `deepvk/USER-bge-m3` | 0.817 |
| `BAAI/bge-m3` | 0.820 |
| `intfloat/multilingual-e5-large` | 0.840 |
| `intfloat/multilingual-e5-large-instruct` | 0.857 |
| `intfloat/multilingual-e5-large-instruct`, дообученная | **0.894** |

Готовые модели хуже BM25 с долями выборов по локациям (0.873). Лучшую из них дообучаем на парах «текст запроса → выбранное объявление» из обучения ретривера. Одинаковые пары оставляем по одному разу, а на один текст берём не больше 20 пар, чтобы частые запросы вроде «маникюр» не заняли всё обучение; остаётся 253 662 пары. Пары подаются в модель пачками по 256: для каждого запроса правильный ответ — его объявление, а 255 объявлений других пар этой пачки считаются неправильными. Модель учится делать вектор запроса ближе к своему объявлению, чем к чужим. Один проход по всем парам занял 38 минут на RTX 4090.

После дообучения поиск по смыслу сам по себе лучше бейзлайна с фильтрами: Recall@50 = 0.894 против 0.885. В первые 1000 объявлений он ставит 99.1% правильных объявлений, а бейзлайн — 98.0%. Поэтому поиск по смыслу полезен как второй источник кандидатов.

## Всё вместе

[`ranking/dense.ipynb`](notebooks/ranking/dense.ipynb)

Кандидаты — объединение первых 500 кандидатов бейзлайна и первых 200 результатов поиска по смыслу, в среднем 596 на запрос. Среди них 98.8% правильных объявлений, а среди одних первых 500 кандидатов бейзлайна — 96.9%. К признакам реранкера добавляются пять признаков эмбеддера: косинус, косинус относительно максимального по запросу, оценка поиска по смыслу с учётом локации, место кандидата в выдаче поиска по смыслу и доля объявлений той же подкатегории среди первых 30 результатов поиска по смыслу.

| | Recall@50 |
|---|---|
| бейзлайн | 0.885 |
| поиск по смыслу, первые 50 | 0.894 |
| реранкер с прежними признаками, но на всех кандидатах | 0.912 |
| + признаки эмбеддера | 0.946 |
| + половина валидации в обучении (качество считаем на другой половине, затем половины меняем местами) | **0.950** |

Само расширение списка кандидатов даёт немного (0.907 → 0.912), главное дают признаки эмбеддера: +3.3 п.п. Итоговое решение сильнее всего помогло там, где бейзлайн был слабее всего: на запросах из одного слова (0.78 → 0.91) и на запросах, где правильное объявление лежит не в локации поиска (0.74 → 0.86). Реранкер без эмбеддингов из раздела «Реранкинг» поднимал обе группы только до 0.80.

Последняя строка таблицы — про то, на чём учить реранкер. Запросы реранкера устроены не так, как тест: все подходящие новые тексты забрала валидация, поэтому у реранкера почти одни знакомые тексты. Эмбеддер видел при дообучении 89% текстов запросов реранкера, но почти всегда с другими объявлениями. У валидации таких текстов 32%, у теста — 28% (`embeddings/models.ipynb`). Эти доли не совпадают с 37% из раздела «Валидация»: здесь текст берётся вместе с фильтрами и сравнивается только с тем, на чём учился эмбеддер. Реранкер, обученный только на знакомых текстах, вероятно, доверяет эмбеддеру больше, чем стоит для новых.

Если добавить в обучение половину проверочных запросов, а качество считать на другой половине (и наоборот), Recall@50 растёт на 0.5 п.п. Это согласуется с тем, что реранкеру полезно учиться на запросах, похожих на тест. Но часть прироста может давать и то, что обучающих запросов просто стало больше, и этот опыт две причины не разделяет. В любом случае валидация в обучении помогает, поэтому итоговая модель учится на запросах реранкера и всей валидации. Честно измерить её на валидации уже нельзя, лучшая оценка — 0.950. На лидерборде она даёт **0.922**.

## Как воспроизвести

Нужны Python 3.12, [uv](https://docs.astral.sh/uv/) и файлы `train.parquet`, `benchmark_queries.parquet`, `benchmark_items.parquet` в папке `data/`. Сначала общие шаги, потом один из двух вариантов.

Установить зависимости:

```bash
uv sync
```

Прочитать исходные файлы:

```bash
uv run python scripts/ingestion/ingest.py
```

Обработать тексты:

```bash
uv run python scripts/processing/process.py
```

Разделить train на валидацию, обучение реранкера и обучение ретривера:

```bash
uv run python scripts/validation/split.py
```

Подготовить тексты для эмбеддера (видеокарта не нужна; без этого шага не запустятся ноутбуки `embeddings/models.ipynb` и `ranking/dense.ipynb`):

```bash
uv run python scripts/embeddings/prepare.py
```

**Вариант 1, без видеокарты.** Дообученная модель, её векторы корпуса и запросов, метрики всех моделей, лог дообучения и готовая модель LightGBM лежат на [Яндекс Диске](https://disk.yandex.ru/d/ona9WBTZhDd2mA). Распаковать архив в корень репозитория:

```bash
tar -xzf avito_artifacts.tar.gz
```

Посчитать кандидатов с признаками (векторы берутся из архива):

```bash
uv run python scripts/ranking/candidates.py
```

Построить ответ `data/submissions/answer.csv` моделью LightGBM из архива:

```bash
uv run python scripts/submission/answer.py
```

**Вариант 2, с видеокартой: всё считаем сами.** Установить библиотеки для видеокарты:

```bash
uv sync --extra gpu
```

Закодировать корпус готовыми моделями и сравнить их (необязательно):

```bash
uv run python scripts/embeddings/encode.py --models e5-base e5-large e5-large-instruct bge-m3 user-bge-m3
```

Дообучить модель:

```bash
uv run python scripts/embeddings/finetune.py --model e5-large-instruct
```

Посчитать кандидатов с признаками:

```bash
uv run python scripts/ranking/candidates.py
```

Обучить LightGBM на запросах реранкера и всей валидации (этой же командой обучена модель из архива):

```bash
uv run python scripts/ranking/train.py
```

Построить ответ `data/submissions/answer.csv`:

```bash
uv run python scripts/submission/answer.py
```

**Необязательно, в любом варианте.** Кандидаты одного BM25 для ноутбука `ranking/ranker.ipynb`:

```bash
uv run python scripts/ranking/candidates.py --bm25-only
```

Ответы бейзлайна `data/submissions/bm25_prior.csv` (без фильтров) и `data/submissions/bm25_prior_filters.csv` (с фильтрами):

```bash
uv run python scripts/submission/baseline.py
```

Использованы открытые библиотеки LightGBM, sentence-transformers, PyTorch, PyStemmer, polars, NumPy, SciPy, scikit-learn и открытая модель `intfloat/multilingual-e5-large-instruct`; для сравнения — модели из таблицы выше. Всё запускается локально, без внешних API; во втором варианте модели один раз скачиваются с HuggingFace.
